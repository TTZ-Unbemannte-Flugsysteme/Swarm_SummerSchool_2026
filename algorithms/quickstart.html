Swarm_SummerSchool_2026 · quickstart

Clone it, install it, fly it

Everything you need is on this page: three drones flying a formation in Gazebo, with a browser that flies the leader. You have not seen this repository before, and nothing is set up on your machine. That is the assumption throughout.

Needs Ubuntu 22.04 or 24.04 Disk about 10 GB Time 30–40 min Typing 5 commands
Most of that time is not yours. It is the ArduPilot compile, which runs unattended. You type five commands; the machine does the rest. If you only have half an hour, start step 2 and go and get a coffee.

1 Clone the branch

about a minute

# the -b matters: that branch is the one with the simulation on it
git clone -b simulation https://github.com/TTZ-Unbemannte-Flugsysteme/Swarm_SummerSchool_2026.git
cd Swarm_SummerSchool_2026

Leave off -b simulation and you land on the default branch, where none of this exists. It is the single commonest way to start confused.

2 Install everything

30–40 minutes, nearly all of it unattended

./install.sh

It asks for your sudo password early, for the system packages, then asks once more before the long compile. Answer y and leave it alone. ./install.sh --yes skips both questions.

What it is doing, so the wait makes sense:

  • system build tools, then Gazebo Harmonic and its Python bindings — the 3D physics and the cameras
  • ArduPilot SITL, cloned and compiled — the real autopilot firmware, built to run on your machine instead of on a flight controller. This is the long part.
  • the ardupilot_gazebo plugin, which joins the two together
  • the Python packages, then a record of where it all went, and flyit onto your PATH
If it fails partway

Run ./install.sh again. Every step checks whether its own work is already done, so a second run resumes where the first stopped rather than starting the compile over. A failed install is not a reason to delete anything and begin again.

3 Check the machine

seconds — but open a new terminal first

flyit --check
Open a new terminal for this

The installer added ~/.local/bin to your PATH, and the terminal you ran it in does not know that yet — a shell reads its PATH once, at startup. A new terminal picks it up. If flyit is still not found, use ./flyit --check from inside the repository, which works either way.

One line per dependency, then a verdict:

ArduPilot SITL
ok checkout /home/you/swarm-deps/ardupilot
ok arducopter binary built (ArduPilot-4.6.0-beta1-7764-g06a33a1de4)
Gazebo
ok gz sim 8.10.0
warn gz python bindings missing - dashboard runs, camera feeds do not

RESULT: PASS - ready to run: flyit

You want PASS. Lines marked warn are fine — they cost you one feature, not the simulation. Lines marked FAIL print the fix directly underneath them.

This check exists to answer one question before you waste time on any other: is my machine missing something, or is the simulation broken? Those two have completely different fixes and look identical from the outside.

4 Fly

a couple of minutes on the first launch

flyit

Four terminal windows open — the vehicles, the position relay, the flight log, the dashboard — plus a Gazebo window with three quadrotors on a runway.

The four terminals are not clutter: each one is a component you can watch, and when something misbehaves, that is where it says so. Leave all of it running — the dashboard is the next step.

5 Open the web dashboard

this is the thing you look at

http://127.0.0.1:8760

flyit opens a browser there for you. If no browser appears, type that address in yourself — which is what happens over SSH, on a machine with no desktop, or when you used --no-terms.

Is it even serving?

You can ask it without a browser:

curl -s http://127.0.0.1:8760/api/status | head -c 120

A line of JSON beginning {"now": means the dashboard is up and the page will load. Nothing at all means it never started — look at the terminal titled swarm: dashboard, which will say why.

Running the simulation on another machine

The dashboard listens on loopback only, and that is deliberate: it can arm and fly the vehicles, so it is not something to put on a shared network. Reach it through a tunnel rather than exposing it.

ssh -L 8760:127.0.0.1:8760 you@that-machine

Leave that running, then open http://127.0.0.1:8760 on your own laptop. The traffic rides the SSH connection you already trust, and nothing new is opened to the network.

If the page loads but is empty

Port 8760 may already be taken by something else — often a dashboard left over from a previous run that flyit --stop would have cleared. Either stop it, or move this one: DASHBOARD_HTTP_PORT=8761 flyit, then use that port in the address.

6 What to do in it

the part you came for

Wait about a minute first

The buttons start disabled and enable themselves. GPS and the EKF — the filter that fuses the sensors into one position estimate — need time to settle, and arming before they have is how a real aircraft flies into the ground. Nothing is stuck. You do not click anything to make it happen.

  1. Arm + take off all (20 m)
    All three lift off and hold at 20 m.
  2. Followers → FOLLOW
    Drones 2 and 3 take station behind drone 1. This is the whole point of the system: they are now holding a formation on their own, in the autopilot, not because a script is nudging them.
  3. Then any of:
    • Take control — fly drone 1 from the keyboard. W A S D for north/west/south/east, R F for up/down, Q E to yaw. The other two follow you.
    • Click the map — drone 1 flies to that point, formation intact.
    • Inspect the highway or Inspect the whole area — the swarm surveys on its own, finds the staged accident, and reports it with a position and a photo.
  4. Land all when you are done.
What to watch

The Station error chart, while the formation settles. That number — how far each follower is from where it should be — is what the entire system exists to hold small. Everything else on the page is there to explain that one line.

7 Stop

flyit --stop
Closing the windows is not enough

The simulator keeps running without them. Always stop it this way. A leftover run holds the network ports the next one needs, so the next flyit refuses to start rather than quietly flying half a swarm against the wrong vehicles.

Other ways to run it

flyit 2            # two drones instead of three
flyit --no-gazebo  # no 3D window: headless, starts in seconds
flyit --no-terms   # no windows at all, everything in the background
flyit --help       # all options

--no-gazebo is the one to remember on a slow laptop or over SSH. The formation is ArduPilot's own, so it behaves identically — you simply cannot see it, and there are no cameras.

Prove it works, without watching

There is a scripted version that flies the formation, measures it, and tells you whether it held. Leave flyit running and, in another terminal:

python3 scripts/leader_follower.py --vehicles 3
follower1: closest 0.0m, settled 0.0m (tolerance 6m)
follower2: closest 0.0m, settled 0.0m (tolerance 6m)
RESULT: PASS - every follower held station within 6m.

It exits non-zero on failure, so it works in a script as well as on a screen. Nothing in this repository asks you to judge a result by eye.

When something goes wrong

Run flyit --check first, always. It separates “my machine is missing something” from “the simulation is broken”, and that is most of the problem solved.

What you seeWhat it means
flyit: command not found You have not opened a new terminal since installing../flyit — from inside the repository
no SITL binary at ... The install did not finish. Re-running resumes it../install.sh
ERROR: vehicles did not come up The last lines of the vehicle's own log say why.tail .run/latest/vehicle0.log
The dashboard will not load Something else already holds port 8760.flyit --stop  or  DASHBOARD_HTTP_PORT=8761 flyit
Buttons stay greyed out GPS and the EKF are not ready. Give it another minute — this is the system protecting you, not a fault.
Camera panels stay black The Gazebo Python bindings are missing. Everything else works.flyit --check — it names the package
It refuses to start, says processes are alive A previous run is still up, and stacking a second on top would fly the wrong vehicles.flyit --stop

Every run keeps its own logs

.run/latest/ is always the newest run, and .run/latest/flight_log.txt is the merged log of all three drones — modes, arming, and every message the autopilot sent:

15:54:03    30.5s drone 1  MODE      STABILIZE -> GUIDED
15:54:04    30.9s drone 1  ARMED     in GUIDED
15:54:17    44.6s drone 2  MODE      GUIDED -> FOLLOW

That file answers most questions about why a drone did, or did not, do something. When the vehicles once refused to arm, it said so in one line: PreArm: Motors: Check frame class and type.

Already have ArduPilot built?

Skip the compile entirely. Point at the directory that contains your ardupilot checkout:

export SSS_ROOT=/path/to/parent
./install.sh --no-apt
This is the short path.
