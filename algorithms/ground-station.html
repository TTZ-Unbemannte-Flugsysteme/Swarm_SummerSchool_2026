00 — What this is for

Why attach a ground station at all

The dashboard in this repo was built for one job: watching and flying a formation. A ground station is the other half — the general-purpose tool you will actually use on the aircraft, for the things a purpose-built page does not do.

  • Parameters. Browse and edit every FOLL_* value live, instead of through a script.
  • Missions. Draw waypoints on a map and upload them.
  • Calibration and setup screens — the ones you will need on the real F450.
  • A second opinion. If the dashboard and QGroundControl disagree, one of them has a bug, and that is worth knowing.

QGroundControl speaks ArduPilot natively, so nothing about the simulation has to change to accommodate it. Mission Planner works too — flyit --mp — and everything on this page applies to it equally.

01 — The design

One link for the whole swarm

Each drone already has five UDP ports of its own, one per consumer, because a UDP port has exactly one owner. A ground station could attach to a drone's own 14553 + 10i port — but then you would need one link per drone and three windows to watch three aircraft.

So every vehicle also forwards to one shared endpoint. MAVLink messages carry the sender's system ID, so three streams arriving on one port are simply three vehicles, and a ground station lists them as such.

Why you have to add the link by hand

QGroundControl connects automatically on UDP 14550, and that would be the obvious choice — except that 14550 is the first drone's relay port, and relay.py binds it. Two programs cannot own one UDP port, and the relay is what carries the leader's position to the followers: the formation exists because of it.

The alternative was renumbering every port in the repo so the automatic connection would land somewhere free. The port scheme is quoted in three documents and every consumer's source, so a one-time link in a dialog is the smaller cost. It is also the more honest lesson: on a real system you rarely get to choose the port you wanted.

02 — Launch

1Start the simulation with it

$ flyit --qgc            # three drones + QGroundControl
$ flyit --mp             # Mission Planner instead

flyit finds the AppImage in your home directory or next to the other dependencies. If yours lives somewhere else, tell it once:

$ export QGROUNDCONTROL=~/Downloads/QGroundControl-x86_64.AppImage

or put the same line in config/local.env, which is gitignored and read on every run.

AppImages need FUSE. Where it is missing, flyit notices what the launch actually wrote to its log and retries with --appimage-extract-and-run, which is AppImage's own documented fallback. It starts more slowly and is otherwise identical.

03 — Once, ever

2Add the link

In QGroundControl: Application Settings → Comm Links → Add.

Comm Link Settings
Name
swarm
Type
UDP
Listening port
14540
Target hosts
leave empty
Automatically Connect on Start
ticked

Then OK and Connect. Leave the target hosts list empty on purpose: the simulation sends to QGroundControl first, so it learns where to reply from the traffic it receives. Naming a target host as well does no harm but is one more thing to get wrong.

With Automatically Connect on Start ticked, every later run just works — start the simulation, start QGroundControl, and the drones appear.

04 — Verify

3Check it worked

You should see three vehicles, selectable individually, each with its own attitude, battery and GPS. If you only see one, the link is attached to a per-drone port rather than the shared one.

You do not need the GUI to prove the endpoint is live. This is the same thing QGroundControl does — bind the port and see who turns up:

$ python3 - <<'EOF'
from pymavlink import mavutil
import time
c = mavutil.mavlink_connection("udpin:127.0.0.1:14540")
seen = set()
t0 = time.time()
while time.time() - t0 < 20 and len(seen) < 3:
    m = c.recv_match(type="HEARTBEAT", blocking=True, timeout=3)
    if m: seen.add(m.get_srcSystem())
print("vehicles on the shared link:", sorted(seen))
EOF
vehicles on the shared link: [1, 2, 3]
05 — The part that surprises people

Three vehicles on one port, and commands still land on one

If all three drones share a link, what stops a mode change going to all of them? Nothing about the transport — the datagram may well reach every MAVProxy. What stops it is the message: every MAVLink command carries a target_system, and a vehicle ignores anything addressed to a different system ID.

Measured on this build: a SET_MODE addressed to system 2, sent once into the shared port, moved drone 2 into GUIDED and left drones 1 and 3 in STABILIZE.

One thing worth noticing on a shared network

QGroundControl's automatic link binds 0.0.0.0:14550 — every interface, not just loopback. It coexists with the relay's 127.0.0.1:14550 as far as binding goes, because a more specific binding wins for loopback traffic — but it is not harmless: it attaches to drone 1 as a ground station and feeds it centred virtual sticks, after which the leader refuses to arm because a copter arms with the throttle down. Untick AutoConnect → UDP and use only the link you added. But it does mean a ground station is listening on the room's network. Everything this repo starts binds loopback only, deliberately; a GCS is the one component that does not, and on a shared Wi-Fi that is worth knowing before you wonder why someone else's drone appeared in your vehicle list.
